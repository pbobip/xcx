## 1. Problem Statement / 问题陈述

顾客需要一个可信、步骤简单的微信小程序，用于浏览不同游戏的陪玩、护航或代打服务，选择明确的服务套餐，在线支付，并持续查看人工派单与履约进度。

当前参考产品虽然具备游戏分类、套餐列表和支付入口，但如果直接复制普通商城，会遇到以下问题：

- 普通商品订单无法准确表达“待派单、已派单、服务中、待确认”等服务履约状态；
- 不同游戏、不同服务类型需要不同的下单参数；
- 陪玩与代打的账号安全、退款规则和履约证据不同；
- 支付成功、人工派单、服务完成和售后之间需要一致、可追踪的状态流转；
- 首版无需建设选手入驻、抢单、分账和自建聊天，避免把简单自营业务做成复杂平台。

## 2. Product Goals / 产品目标

### 2.1 核心目标

1. 建立从浏览、下单、微信支付、人工派单、履约到售后的完整闭环。
2. 让运营人员可在后台维护游戏、服务分类、套餐、价格和派单状态，无需改代码。
3. 让顾客始终清楚当前订单状态、下一步动作、退款条件和客服入口。
4. 在首版严格控制账号凭证、支付、隐私、品牌素材和宣传文案风险。

### 2.2 成功指标

上线后按周观察：

- 商品详情到提交订单转化率；
- 提交订单到支付成功率；
- 支付成功至首次派单的中位时长；
- 已支付订单的履约完成率；
- 退款申请率、退款成功率和投诉率；
- 客服咨询率及主要咨询原因；
- 各游戏、服务类型和套餐的销售额与复购率。

首月指标基线以真实运营数据建立，不在开发阶段虚设业务增长目标。

## 3. Solution / 解决方案

建设一个单商户自营的微信服务商城：

- 顾客在小程序中按游戏、服务分类和套餐浏览；
- 顾客填写区服、平台、时间和服务目标等必要参数；
- 顾客阅读服务规则后使用微信支付；
- 运营人员在后台选择内部服务人员并人工派单；
- 运营人员按实际进度更新订单；
- 顾客查看进度、确认完成或发起售后；
- 客服使用微信原生客服能力处理咨询和争议；
- 系统记录支付、派单、状态变更、退款和后台操作日志。

首版不向外部选手开放注册或抢单，不自动向服务人员分账。

## 4. Scope / 产品范围

### 4.1 P0：首版必须具备

- 微信静默登录与平台用户账户；
- 手机号授权或手工填写的联系信息；
- 首页、游戏分类、服务套餐、套餐详情；
- 动态下单参数和价格快照；
- 微信支付 APIv3；
- 订单列表、订单详情和履约时间线；
- 后台人工派单与状态更新；
- 顾客确认完成；
- 取消未支付订单、退款申请与后台处理；
- 微信原生客服；
- 用户协议、隐私政策、服务规则和退款规则；
- 游戏、分类、套餐、价格、上下架、人员和订单后台管理；
- 支付、退款、状态变化和操作审计日志。

### 4.2 P1：首版稳定后增加

- 顾客授权后的微信订阅消息；
- 服务人员简单移动工作台；
- 服务评价与标签；
- 常用游戏信息复用；
- 运营数据看板和导出；
- 优惠码或新客优惠，前提是不影响核心订单模型。

### 4.3 服务类型开关

| 服务类型 | 首版状态 | 下单方式 | 账号安全要求 |
|---|---|---|---|
| 陪玩 | 默认开启 | 按小时、局数或套餐 | 仅收集游戏昵称/ID、区服和组队信息，不收集密码 |
| 护航 | 默认开启 | 按小时、局数、任务或目标套餐 | 优先采用顾客本人在线组队模式，不收集密码 |
| 代打 | 默认关闭，逐游戏审核后开启 | 按阶段、局数或明确目标套餐 | 小程序和后台不得采集、展示或存储明文账号密码；上线前必须完成规则和风险评审 |

任何“外挂、脚本、刷量、账号买卖、道具交易”均不属于本 PRD 范围。

## 5. Actors and Permissions / 角色与权限

### 5.1 顾客

- 浏览已上架服务；
- 登录、维护必要联系信息；
- 下单、支付、查看进度；
- 取消未付款订单；
- 确认完成、申请退款或联系客服；
- 查看本人订单和售后记录。

### 5.2 运营人员

- 管理游戏、分类、套餐、动态参数和价格；
- 查看已支付订单；
- 选择服务人员并人工派单；
- 更新履约状态和内部备注；
- 处理退款、售后和异常订单；
- 查看基础业务数据。

### 5.3 客服人员

- 查看处理咨询所需的最小订单信息；
- 记录客服结论、退款建议和争议凭证；
- 不得查看支付私钥、完整敏感凭证或无权限的后台配置。

### 5.4 财务人员

- 查看支付、退款和对账流水；
- 按权限导出脱敏财务数据；
- 处理对账差异，但不能修改商品、派单或履约状态。

### 5.5 管理员

- 管理后台账户、角色和权限；
- 管理支付、通知、协议和系统配置；
- 查看审计日志；
- 执行运营人员不可执行的高风险操作。

### 5.6 内部服务人员

首版由运营人员在线下联系服务人员，系统只保存服务人员基础档案和派单记录。服务人员不自行注册、不抢单、不直接登录顾客端小程序。

## 7. Core User Flow / 核心用户流程

### 7.1 正常履约流程

1. 顾客进入小程序，可先浏览后登录。
2. 顾客选择游戏、服务分类和套餐。
3. 顾客填写该套餐要求的动态参数。
4. 系统实时展示最终价格、服务范围、预计响应时间和退款规则。
5. 顾客确认协议并提交订单。
6. 服务端创建未支付订单并锁定套餐、选项、文案和价格快照。
7. 顾客发起微信支付。
8. 服务端收到经过验签的支付通知后，将订单置为“待派单”。
9. 运营人员选择内部服务人员并记录派单。
10. 运营人员将订单依次更新为“已派单”“服务中”“待顾客确认”。
11. 顾客确认完成，订单进入“已完成”。
12. 顾客可在售后有效期内联系客服或提交问题。

### 7.2 未支付取消流程

- 顾客可主动取消未支付订单；
- 未支付订单默认 30 分钟自动关闭；
- 已关闭订单不得继续使用旧支付参数付款；
- 顾客可重新提交新订单，重新锁定价格。

### 7.3 退款流程

1. 顾客从订单详情选择退款原因并补充说明。
2. 系统根据履约阶段展示预计可退范围，不自动承诺固定金额。
3. 运营或客服审核退款。
4. 管理员确认退款金额后，服务端调用微信支付退款接口。
5. 系统以退款通知或主动查询结果更新退款状态。
6. 顾客在订单详情查看退款金额和进度。

## 8. Order State Model / 订单状态模型

支付状态、履约状态和售后状态必须分开保存，避免一个字段承担所有含义。

### 8.1 支付状态

| 状态 | 含义 |
|---|---|
| 未支付 | 已创建订单，尚未确认收款 |
| 支付中 | 已获得预支付参数，等待可靠支付结果 |
| 已支付 | 已通过验签通知或主动查单确认付款 |
| 部分退款 | 已退回部分订单金额 |
| 已退款 | 已退回全部实付金额 |
| 已关闭 | 未支付订单已超时或主动取消 |

### 8.2 履约状态

| 状态 | 顾客可见说明 | 允许的下一状态 |
|---|---|---|
| 待付款 | 等待付款 | 待派单、已取消 |
| 待派单 | 已付款，等待安排服务 | 已派单、售后处理中 |
| 已派单 | 已安排服务人员 | 服务中、售后处理中 |
| 服务中 | 服务正在进行 | 待确认、售后处理中 |
| 待确认 | 服务人员已提交完成 | 已完成、售后处理中 |
| 已完成 | 顾客已确认或确认时限已到 | 售后处理中 |
| 已取消 | 未付款订单已取消 | 终态 |

顾客确认默认时限为 24 小时，可由后台配置。顾客在时限内提出问题时，暂停自动完成。

### 8.3 售后状态

无售后、申请中、审核通过、退款中、已退款、已驳回、争议处理中、已关闭。

所有状态变更必须保存操作者、来源、时间、原状态、新状态和备注。

## 9. Functional Requirements / 功能需求

### 9.1 登录与用户资料

- 用户可在未登录状态浏览商品；
- 下单前必须完成微信登录；
- 首次下单必须提供可联系手机号，可使用微信手机号授权或手工输入并验证；
- 系统以平台用户 ID 作为业务主键，不以昵称或手机号直接作为主键；
- 顾客只能查看本人的订单、退款和联系信息；
- 支持用户申请注销和删除非依法必须保留的个人信息。

### 9.2 游戏与分类

- 首批游戏：英雄联盟、永劫无间、三角洲行动、王者荣耀、绝地求生、无畏契约；
- 后台必须区分端游/手游、PC/移动端及实际产品版本，不能只用游戏名称代替履约范围；
- 游戏支持排序、启用/停用、封面、说明和服务规则；
- 同一游戏下可配置多个服务分类；
- 服务分类支持排序、启用/停用和运营文案；
- 下架游戏或分类不影响历史订单快照和查询。

### 9.3 套餐与动态参数

- 套餐归属于一个游戏和一个服务分类；
- 套餐包含名称、简介、服务类型、主图、详情、基础价格、预计响应时间、服务范围、退款说明和上下架状态；
- 支持文本、数字、单选、多选、日期时间等动态字段；
- 套餐可配置“立即服务”“预约服务”或两者均支持；
- 立即服务仅在营业时间且运营开启接待时可售，预约服务只允许选择可售时段；
- 字段可设置必填、可选、说明、校验规则和是否影响价格；
- 价格计算结果在提交订单前必须明确展示；
- 订单保存套餐、选项、文案、服务规则和实付价格快照；
- 后台改价不得影响历史订单。

### 9.4 订单创建

- 服务端重新校验套餐状态、动态参数和最终价格；
- 首版一张订单只包含一个服务套餐；局数、小时数或数量作为套餐参数，不建设购物车；
- 金额统一以整数“分”存储和计算；
- 同一提交请求不得因重复点击创建多个有效订单；
- 订单编号必须全局唯一且不可由顾客猜测其他订单；
- 提交前必须勾选服务规则和退款规则；
- 订单备注不得填写账号密码、支付密码、验证码或身份证明等敏感凭证；
- 对疑似敏感凭证的输入进行阻止或提醒。

### 9.5 微信支付

- 仅服务端调用微信支付 APIv3 预下单；
- 小程序端仅接收调起支付所需的短期参数；
- AppSecret、商户私钥、APIv3 密钥不得进入前端包、日志或普通后台页面；
- 支付通知必须验签、解密并进行金额、商户号、订单号校验；
- 支付通知和退款通知必须支持重复投递且结果幂等；
- 顾客取消支付不等于订单取消；
- 支付结果不确定时，订单页应主动查单，不向顾客错误展示已支付；
- 支持关单、退款和日常对账。

### 9.6 人工派单

- 仅已支付且无有效全额退款的订单可派单；
- 运营人员可按游戏、时间、状态筛选待派单订单；
- 运营人员选择一个内部服务人员并填写内部派单备注；
- 运营人员在线下取得服务人员确认后，才可把订单标记为“已派单”；单方面选中人员不等于已确认履约；
- 更换服务人员必须记录原因和前后人员；
- 顾客端只展示必要的服务联系信息，不展示内部备注；
- 派单后顾客可查看“已安排服务人员”，是否展示昵称/头像由后台配置；
- 首版服务人员无公开主页、无顾客选择服务人员功能。

### 9.7 履约进度

- 运营人员只能按允许的状态路径更新订单；
- 服务开始、提交完成必须记录时间；
- 运营人员可添加顾客可见进度说明和仅内部可见备注；
- 售后争议需要凭证时，只保存完成处理所必需的截图或记录，并限制查看权限与保存期限；
- 顾客可在订单详情查看时间线；
- 订单处于售后处理中时，不得自动完成；
- 所有高风险手工修正必须由管理员操作并记录原因。

### 9.8 顾客确认与售后

- 顾客可确认服务完成；
- 待确认超过配置时限且无争议时自动完成；
- 顾客可选择未派单、无法履约、服务不符、重复付款等标准退款原因；
- 退款金额不得超过剩余可退金额；
- 已服务部分的退款由运营依据公开规则人工审核；
- 驳回退款必须填写顾客可见理由；
- 退款失败可重试，但不得创建重复退款；
- 顾客可随时从订单详情进入微信客服。

### 9.9 客服

- 使用微信原生客服入口，不自建即时聊天；
- 客服入口在套餐详情、确认订单、订单详情和“客服”Tab 均可访问；
- 客服人员根据订单号查找订单；
- 后台可记录咨询分类、处理摘要和后续动作；
- 不将完整支付凭证、密钥或账号密码复制到客服记录。

### 9.10 内容与协议

- 游戏图片、Logo、角色图和商品素材必须来自有权使用的来源；
- 后台支持维护用户协议、隐私政策、服务规则和退款规则版本；
- 下单时保存顾客同意的协议版本；
- “必出、百分百、永久安全、零风险”等绝对化承诺默认禁止；
- 代打相关套餐必须经过逐游戏运营审核后才能开启。

### 9.11 管理后台

- 采用角色权限控制，不以共享管理员账户运营；
- 关键操作包括改价、手工改状态、派单、更换人员、批准退款和修改支付配置；
- 关键操作必须二次确认并留审计记录；
- 列表支持必要筛选、分页和导出；
- 导出内容按权限脱敏；
- 支付私钥和 APIv3 密钥不允许在页面明文回显。

## 10. User Stories / 用户故事

1. 作为访客，我希望不登录也能浏览游戏和套餐，以便先判断是否有需要的服务。
2. 作为顾客，我希望通过微信快速登录，以便无需单独注册密码账户。
3. 作为顾客，我希望在首次下单时留下可联系手机号，以便运营人员及时确认服务。
4. 作为顾客，我希望按游戏切换服务，以便快速找到对应内容。
5. 作为顾客，我希望按陪玩、护航等类型筛选套餐，以便减少无关信息。
6. 作为顾客，我希望看到套餐价格、单位、服务范围和预计响应时间，以便做出购买决定。
7. 作为顾客，我希望详情页明确展示退款规则，以便付款前了解风险。
8. 作为顾客，我希望不同游戏只要求填写必要参数，以便避免重复或无关输入。
9. 作为顾客，我希望选择不同选项后立即看到最终价格，以便避免结算时意外加价。
10. 作为顾客，我希望提交订单前核对游戏、区服、时间、目标和金额，以便纠正错误。
11. 作为顾客，我希望系统阻止我在备注中填写密码和验证码，以便保护账号安全。
12. 作为顾客，我希望通过微信支付完成付款，以便使用熟悉的支付方式。
13. 作为顾客，我希望支付取消后仍能回到订单继续处理，以便不会误以为订单丢失。
14. 作为顾客，我希望支付成功由系统可靠确认，以便不会出现扣款后仍显示未付款。
15. 作为顾客，我希望查看全部订单并按状态筛选，以便追踪多个服务。
16. 作为顾客，我希望在订单详情看到当前进度和时间线，以便知道平台正在做什么。
17. 作为顾客，我希望付款后看到预计派单时间，以便合理安排游戏时间。
18. 作为顾客，我希望派单后知道已经安排服务人员，以便安心等待履约。
19. 作为顾客，我希望在服务开始前获得清晰状态提示，以便按时上线配合。
20. 作为顾客，我希望服务结束后确认完成，以便表达实际履约结果。
21. 作为顾客，我希望对有问题的订单暂停自动完成并联系客服，以便保留申诉机会。
22. 作为顾客，我希望未付款订单可以取消，以便清理不再需要的订单。
23. 作为顾客，我希望未派单订单能申请退款，以便平台无法及时服务时收回款项。
24. 作为顾客，我希望看到退款审核进度和结果，以便了解资金何时退回。
25. 作为顾客，我希望退款被拒绝时看到明确理由，以便决定是否继续申诉。
26. 作为顾客，我希望从任何关键页面进入微信客服，以便遇到问题时快速求助。
27. 作为顾客，我希望查看并同意当前版本的服务规则，以便明确双方责任。
28. 作为顾客，我希望申请注销账户和删除不再需要的数据，以便控制个人信息。
29. 作为运营人员，我希望创建和排序游戏，以便控制前台展示。
30. 作为运营人员，我希望配置服务分类和套餐，以便无需开发即可调整业务。
31. 作为运营人员，我希望为不同套餐配置不同下单字段，以便收集正确履约信息。
32. 作为运营人员，我希望调整套餐上下架和价格，以便快速响应运营变化。
33. 作为运营人员，我希望后台改价不影响历史订单，以便避免订单争议。
34. 作为运营人员，我希望筛选待派单订单，以便优先处理等待时间最长的顾客。
35. 作为运营人员，我希望从内部人员档案选择服务人员，以便记录责任归属。
36. 作为运营人员，我希望更换服务人员时填写原因，以便追溯异常派单。
37. 作为运营人员，我希望按实际进度更新订单，以便顾客看到可信状态。
38. 作为运营人员，我希望内部备注与顾客可见说明分开，以便保护运营信息。
39. 作为运营人员，我希望查看付款是否经过可靠确认，以便不为未付款订单派单。
40. 作为运营人员，我希望处理部分或全部退款，以便按实际履约程度解决售后。
41. 作为运营人员，我希望看到退款失败原因并安全重试，以便不重复退款。
42. 作为客服人员，我希望使用订单号快速定位订单，以便缩短处理时间。
43. 作为客服人员，我希望记录问题分类和处理结论，以便后续复盘常见投诉。
44. 作为管理员，我希望为不同岗位配置最小权限，以便降低误操作和数据泄露风险。
45. 作为管理员，我希望查看关键操作审计日志，以便追踪改价、派单和退款责任。
46. 作为管理员，我希望密钥永不在普通后台明文显示，以便保护支付安全。
47. 作为管理员，我希望配置未支付超时和顾客确认时限，以便适应运营规则变化。
48. 作为管理员，我希望停用高风险服务类型，以便在审核或规则变化时立即止损。
49. 作为经营者，我希望查看游戏、套餐、支付、派单和退款指标，以便改进经营效率。
50. 作为经营者，我希望所有商品素材都有来源记录，以便降低知识产权风险。
51. 作为顾客，我希望选择立即服务或预约服务，以便按自己的时间接受服务。
52. 作为顾客，我希望自愿订阅关键订单通知，以便及时获知派单和完成状态。
53. 作为派单员，我希望看到超时和预约临近订单，以便优先处理高风险订单。
54. 作为财务人员，我希望核对支付与退款流水，以便发现漏单或金额差异。
55. 作为管理员，我希望紧急停售某个游戏或套餐，以便应对人员不足、审核或游戏规则变化。

## 11. Business Rules / 业务规则

### 11.1 初始默认规则

- 未支付订单：30 分钟关闭；
- 顾客确认：提交完成后 24 小时，无争议则自动完成；
- 派单目标：在套餐承诺的响应时间内完成首次派单；
- 即时订单：仅在后台配置的营业时间及“可接待”状态下销售；
- 已支付但服务尚未开始：原则上支持全额原路退款；
- 商家无法派单或超过公开承诺时限：原则上支持全额原路退款；
- 服务已经开始：按已完成比例、套餐规则和必要履约记录人工审核退款；
- 售后申请：任何阶段均可联系客服；是否可退款及金额按履约阶段和公开规则判断；
- 代打：默认关闭，不能通过普通商品上下架权限绕过合规开关。

上述时限均后台可配置，但规则变更只影响变更后的新订单。

### 11.2 价格规则

- 套餐基础价与选项加价共同构成应付金额；
- 创建订单时由服务端计算并锁定金额；
- 前端传入金额仅作展示参考，不作为收款依据；
- 实付金额、优惠金额、退款金额分别记录；
- 首版无余额、充值、分销佣金和多商户结算。

### 11.3 未成年人和游戏规则

- 下单前展示适龄、健康游戏和监护提示；
- 平台不得帮助顾客规避实名认证、防沉迷或游戏时长限制；
- 对异常高价、高频或疑似未成年人订单，运营可暂停派单并转人工核实；
- 各游戏建立“允许、限制、禁止”的服务清单，代打按具体游戏及版本独立控制。

### 11.4 账号安全规则

- 陪玩和护航默认不需要顾客交出账号控制权；
- 系统不提供密码字段，不保存明文游戏密码、短信验证码或支付密码；
- 运营人员不得在内部备注中记录上述凭证；
- 代打功能上线前须单独评审逐游戏规则、交接流程和风险提示。

## 12. Data Model Decisions / 数据模型决策

核心实体及关系：

- 用户：微信身份、联系信息、隐私同意状态；
- 游戏：游戏基础信息和启用状态；
- 服务分类：归属于游戏；
- 服务套餐：归属于游戏与分类，定义服务类型和基础价格；
- 参数模板：定义套餐下单字段、校验和价格影响；
- 服务人员：内部档案，不开放自助注册；
- 服务订单：用户、金额、支付、履约与售后状态；
- 订单快照：下单时的商品、选项、规则、协议和价格；
- 派单记录：服务人员、操作人、时间、变更原因；
- 支付记录：商户订单号、微信支付订单号、金额和通知处理结果；
- 退款记录：退款单号、申请金额、批准金额、微信退款状态；
- 状态日志：订单每次状态变化；
- 客服/售后记录：问题分类、说明、处理结论；
- 审计日志：后台关键操作。

支付状态、履约状态、售后状态为独立字段；订单快照不可被后台商品修改覆盖。

## 13. Implementation Decisions / 实现决策

1. **底座**：优先采用 ShopXO 后端和 ShopXO UniApp，利用其用户、商品、订单、支付和后台基础能力；服务订单字段、状态和人工派单作为独立业务扩展实现。
2. **架构**：首版采用模块化单体，不引入微服务、消息中间件集群或多租户体系。
3. **前端**：微信小程序为唯一首发顾客端；H5、App 仅保留技术兼容性，不列入首版验收。
4. **商品模型**：保留商城的游戏/分类/套餐管理能力，订单使用服务履约状态，不伪装成物流发货。
5. **登录边界**：小程序获取一次性登录凭据，服务端完成身份交换并生成自身会话。
6. **支付边界**：封装微信支付适配层；业务模块只调用创建支付、查单、退款等明确接口，不直接处理证书细节。
7. **客服边界**：使用微信原生客服，不建设 WebSocket、消息表和自定义即时聊天。
8. **派单方式**：运营后台人工选择内部服务人员；首版不建设服务人员端。
9. **通知方式**：首版以订单页和客服为可靠信息源；订阅消息作为 P1，不能成为唯一通知通道。
10. **权限**：管理员、运营、客服分权；高风险操作留痕。
11. **敏感数据**：密钥使用安全配置管理；日志脱敏；系统不设计游戏密码存储能力。
12. **素材**：开发环境使用自有占位素材，正式素材由经营主体确认授权后替换。
13. **配置快照**：价格、服务规则、退款规则和协议版本随订单保存，保证可追溯。
14. **可配置规则**：支付超时、确认时限、各服务类型开关和前台展示均通过后台控制。

## 14. API Contract Decisions / 接口契约决策

接口按以下业务边界组织，不在 PRD 固定具体路径：

- 身份：登录、刷新会话、手机号绑定、注销；
- 目录：游戏、分类、套餐、详情、价格试算；
- 订单：创建、列表、详情、取消、确认完成；
- 支付：预支付、支付结果查询、支付通知；
- 派单：待派单列表、分配人员、更换人员、履约状态更新；
- 售后：申请、审核、退款、退款通知、进度查询；
- 内容：协议、隐私政策、服务规则和版本；
- 管理：游戏、分类、套餐、人员、权限、审计和数据统计。

所有写接口必须具备身份验证、权限校验、输入校验和重复提交保护。外部支付通知以微信签名为身份依据，并执行商户号、订单号和金额的业务校验。

## 15. Non-functional Requirements / 非功能需求

### 15.1 性能与可用性

- 除微信等第三方耗时外，核心接口 P95 响应时间目标不超过 800 毫秒；
- 支付通知正常情况下 5 秒内完成验签、幂等处理和订单更新；
- 列表默认分页，不一次加载全部订单或用户；
- 生产环境提供健康检查、错误告警和每日自动备份；
- 初始恢复目标：RPO 不超过 24 小时，RTO 不超过 4 小时。

### 15.2 安全与隐私

- 全站 HTTPS；
- 密钥、证书和敏感配置不进入代码仓库；
- 后台最小权限和高风险操作审计；
- 手机号、OpenID 等数据在日志和导出中脱敏；
- 防止越权查看订单、重复支付、重复退款和状态跳转；
- 定期更新底座与依赖，并在上线前进行漏洞扫描；
- 按隐私政策提供收集说明、用户授权、注销和删除流程。

### 15.3 可维护性

- 业务规则集中在服务订单模块，不散落在页面条件判断中；
- 支付、登录、客服等微信能力通过明确适配边界接入；
- 订单状态流转有统一入口；
- 配置变更、人工修正和退款均可追踪。

## 16. Analytics / 埋点与报表

顾客端记录：

- 首页访问；
- 游戏切换；
- 分类点击；
- 套餐曝光与详情查看；
- 价格试算；
- 提交订单；
- 调起支付、支付成功和支付取消；
- 查看订单；
- 联系客服；
- 提交退款；
- 确认完成。

后台报表至少支持：

- 按日期、游戏、服务类型和套餐统计订单数、实收、退款和完成率；
- 待派单数量及等待时长；
- 服务人员派单量与完成量；
- 退款原因和客服问题分类。

埋点不得记录订单备注、手机号、账号凭证或聊天内容。

## 17. Acceptance Criteria / 验收标准

### 17.1 主业务闭环

1. 运营人员能创建一个游戏、服务分类和可售套餐，并配置至少两个动态下单参数。
2. 顾客能从分类页进入套餐详情，填写合法参数并看到服务端计算的最终价格。
3. 顾客能完成微信登录、联系信息填写、协议确认和订单提交。
4. 顾客支付后，系统仅在可靠支付结果确认后把订单改为待派单。
5. 支付通知重复发送不会重复记账或创建重复订单。
6. 运营人员能为待派单订单选择服务人员，并更新为已派单、服务中和待确认。
7. 顾客能在订单详情看到正确时间线并确认完成。
8. 后台商品改价不会改变该历史订单的商品、规则和金额快照。

### 17.2 退款与异常

1. 未支付订单可主动取消并在 30 分钟后自动关闭。
2. 已关闭订单不能使用旧支付参数继续付款。
3. 顾客能提交退款原因，运营能批准部分或全部退款。
4. 重复退款请求不会造成多退；退款金额不能超过剩余可退金额。
5. 退款通知重复发送不会重复更新或重复生成记录。
6. 售后处理中订单不会自动完成。
7. 所有派单、更换人员、状态修正和退款操作均可在日志中追溯。

### 17.3 权限与安全

1. 顾客无法读取他人的订单、手机号或退款记录。
2. 客服无法修改支付配置或直接批准超权限退款。
3. 运营人员无法绕过状态机把未支付订单改为服务中。
4. 前端包、接口响应、后台页面和普通日志中不存在 AppSecret、商户私钥和 APIv3 密钥。
5. 订单备注明确阻止或警告密码、验证码等敏感内容。
6. 代打开关默认关闭，普通商品编辑权限不能绕过该开关。

### 17.4 体验与内容

1. 六个游戏可正常排序和切换，停用后不再对新顾客展示。
2. 页面在主流微信小程序屏幕尺寸下无内容遮挡或横向溢出。
3. 空列表、加载、支付取消、网络失败和退款失败均有清晰提示和恢复入口。
4. 套餐详情、确认订单和订单详情均可进入微信客服。
5. 正式环境不存在未经确认授权的参考图、游戏 Logo 或角色图片。

## 18. Testing Decisions / 测试决策

### 18.1 测试原则

- 主要验证用户可观察行为和业务结果，不测试内部函数实现细节；
- 首选一个最高层端到端接缝覆盖完整闭环，减少大量脆弱的页面级重复测试；
- 微信登录与支付作为外部边界，使用契约测试和少量真实测试商户联调；
- 状态机、金额与权限等高风险规则使用聚焦的集成测试补充。

### 18.2 主测试接缝

唯一主接缝为：

`后台配置套餐 → 顾客登录并下单 → 微信支付结果确认 → 后台人工派单 → 履约状态更新 → 顾客确认完成/申请退款`

该接缝从公开接口和真实数据存储层验证，不依赖具体页面组件结构。

### 18.3 必测模块

- 登录态与订单数据隔离；
- 游戏、分类、套餐与订单快照；
- 价格试算和服务端金额校验；
- 订单状态流转；
- 支付通知验签、金额校验和幂等；
- 派单、更换人员和权限；
- 退款金额上限、幂等和状态同步；
- 协议版本与审计日志；
- 敏感信息输入与日志脱敏。

### 18.4 上线前验证

- 使用微信开发者工具和至少两台真实手机验证核心流程；
- 使用测试商品完成小额真实支付、查单、退款全链路；
- 验证支付通知延迟、重复、乱序及主动查单恢复；
- 验证后台不同角色权限；
- 执行依赖漏洞扫描、基础安全检查和数据库备份恢复演练；
- 使用正式主体信息完成小程序类目、隐私和支付配置检查。

## 19. Out of Scope / 不在本 PRD 范围

- 外部选手注册、实名认证和入驻审核；
- 抢单大厅、自动派单、智能匹配和复杂排班；
- 服务人员独立小程序或 App；
- 顾客与服务人员的自建即时聊天；
- 多套餐购物车及合并履约订单；
- 多商户、供应商、平台抽佣、自动分账和提现；
- 余额充值、储值卡、分销、直播、拼团和复杂营销；
- 游戏账号、道具或货币交易；
- 外挂、脚本、刷量或规避游戏风控；
- H5、原生 App、PC 顾客端；
- 未取得授权的游戏 Logo、角色图和宣传素材；
- “必出”“百分百上分”等无法客观验收的保证型商品。

## 20. Risks and Mitigations / 风险与应对

| 风险 | 影响 | 首版应对 |
|---|---|---|
| 小程序类目或支付经营范围不匹配 | 审核失败、支付受限 | 开发前用现有主体和商户号确认类目与经营范围 |
| 代打违反个别游戏规则 | 投诉、封号、下架风险 | 逐游戏审核，功能默认关闭，不把代打作为首版上线前提 |
| 未授权游戏素材 | 知识产权投诉 | 开发使用占位素材，正式素材保留授权来源 |
| 顾客填写账号密码 | 账号和隐私事故 | 无密码字段、敏感词阻止、员工制度与日志检查 |
| 支付通知丢失或重复 | 错误派单、重复退款 | 验签、幂等、主动查单和对账 |
| 人工派单超时 | 顾客投诉和退款 | 展示响应时限、待派单看板和超时提醒 |
| 人工排班超卖 | 无人履约、集中退款 | 营业开关、即时接待开关、预约时段限制和紧急停售 |
| 未成年人或规避防沉迷 | 合规、投诉与退款风险 | 适龄提示、异常订单人工核实，禁止规避实名与防沉迷 |
| 服务结果存在争议 | 售后成本高 | 明确可验收范围、履约时间线、客服记录和退款规则 |
| 开源底座安全债务 | 漏洞和维护成本 | 使用受支持运行时、上线审计、依赖升级和定期扫描 |

## 21. Release Plan / 发布策略

### 阶段 1：内部验收

- 使用占位素材和测试套餐；
- 完成支付、派单、履约、退款和权限全链路；
- 运营人员完成后台培训与演练。

### 阶段 2：小范围试运营

- 先开放 1–2 个游戏和少量陪玩/护航套餐；
- 人工监控每笔订单和客服反馈；
- 暂不开启代打；
- 建立真实派单时间、退款原因和咨询问题基线。

### 阶段 3：正式扩展

- 根据试运营数据逐步开放六个游戏；
- 优化套餐参数和派单流程；
- 评估订阅消息、服务人员工作台和评价能力；
- 代打须完成单独评审后按游戏逐项开启。

## 22. Further Notes / 补充说明

### 22.1 已确认事项

- 经营方式：单商户自营；
- 派单方式：后台人工派单；
- 服务方向：陪玩、护航/代打；
- 主体条件：已有可用的经营主体、小程序账号和微信支付商户条件；
- 首版不做外部选手自主接单和平台分账。

### 22.2 开工前仍需运营确认，但不阻塞 PRD 评审

- 首批实际上线的 1–2 个游戏；
- 每个游戏的套餐、价格、响应时限和服务时段；
- 每个名称对应的具体游戏版本、终端平台和区服范围；
- 即时单、预约单的营业时间与接待能力；
- 顾客确认与售后的最终运营时限；
- 陪玩/护航使用游戏昵称、组队码或何种语音协作渠道，并避免诱导站外交易；
- 代打是否需要登录顾客账号；如只能共享长期密码，建议首版不开启；
- 争议处理所需的最小履约凭证、查看权限和保存期限；
- 正式品牌名称、配色和已授权素材；
- 微信客服账号和日常排班；
- 代打是否在首版试运营期保持关闭。
