# 微信游戏服务小程序开源选型调研

日期：2026-07-26

## 一、结论先行

参考截图表面上是“游戏分类 + 服务商品 + 下单支付”，但底部还出现“选手、消息”，因此可能存在两种完全不同的产品：

1. **单商户服务商城**：平台自己售卖服务，顾客下单后由后台人工安排服务人员。
2. **双边派单平台**：选手入驻、自主接单、与顾客聊天，平台抽佣并向选手结算。

两者不能用同一套“换皮商城”方案处理。

- 如果第一版只做单商户、后台人工派单，**优先建议基于 ShopXO + ShopXO UniApp 二次开发**。
- CRMEB 可以用，但更适合已有 PHP/CRMEB 经验的团队；正式上线前必须做运行环境升级、依赖和安全审计。
- 如果必须包含选手端、自主接单、聊天、佣金结算和争议处理，**不建议以 CRMEB 或 ShopXO 的商品订单模型硬改**。应采用小程序前端 + 管理后台脚手架 + 自建派单领域模块。
- 第一版最稳妥的路线是：先完成顾客端、微信支付、订单进度、原生微信客服和后台人工派单；选手端与自动结算放到第二阶段。

## 二、参考截图的业务拆解

截图中能识别出的页面结构：

- 顶部横向游戏切换；
- 左侧服务分类；
- 右侧服务套餐、销量、价格和加入按钮；
- 底部首页、分类、选手、消息、我的；
- “极速派单”“打手”“保底”等服务型订单表达。

建议将商品结构定义为：

`游戏 → 服务分类 → 服务套餐（SKU） → 下单参数 → 服务订单`

例如：

- 游戏：英雄联盟、永劫无间、三角洲行动、王者荣耀、绝地求生、无畏契约；
- 服务分类：新人专区、陪玩、护航、段位服务、指定任务；
- 下单参数：平台、区服、当前状态、目标、数量、期望时间和备注；
- 服务订单状态：待付款、待派单、已接单、服务中、待确认、已完成、退款/争议中。

不要把账号密码作为普通订单字段明文保存。若业务必须由服务人员登录顾客账号，需要先确认游戏发行商规则、账号安全责任及平台审核风险。

## 三、开源项目比较

| 方案 | 许可证与技术 | 小程序能力 | 对本项目的适配 | 结论 |
|---|---|---|---|---|
| [CRMEB](https://github.com/crmeb/CRMEB) | Apache-2.0；ThinkPHP 6、Vue 2、Element UI、UniApp | 仓库包含完整 `template/uni-app`；自带商城、订单、支付和运营后台 | 能较快完成单商户商城，但没有选手入驻、接单、排班、佣金结算和争议处理 | 可选，排第二 |
| [ShopXO](https://github.com/gongfuxiang/shopxo) + [ShopXO UniApp](https://github.com/gongfuxiang/shopxo-uniapp) | MIT；后端要求 PHP ≥8.0；UniApp 前端独立开源 | 官方列明支持微信小程序、H5、App 等多端，支持插件和可视化装修 | 更适合做轻量单商户服务商城，再增加服务订单字段与人工派单 | **单商户 MVP 首选** |
| [litemall](https://github.com/linlinjava/litemall) | MIT；Spring Boot + Vue + 原生微信小程序 | 登录、商品、订单、支付、客服等示例较完整 | README 明确称项目用于学习练习、仍不完善且不承担使用后果 | 不建议新生产项目采用 |
| [Mall4j](https://github.com/gz-yami/mall4j) | AGPL-3.0；Spring Boot 4 + Vue 3 | 开源版聚焦 B2C 基础商城 | README 明确闭源商用需要另行商业授权；双边服务平台仍需大量自建 | 除非接受 AGPL 或购买授权，否则不选 |
| [RuoYi-Vue-Plus](https://github.com/dromara/RuoYi-Vue-Plus) + 自建小程序 | MIT；Java 17/21、Vue 3 | 它本身不是商城，需要自建 UniApp/Taro 小程序和支付模块 | 适合作为双边平台的后台、权限和基础设施脚手架，订单/派单/结算均按业务建模 | **双边平台可选** |

### CRMEB 的关键事实

- 仓库许可证为 [Apache License 2.0](https://github.com/crmeb/CRMEB/blob/master/LICENSE)，允许二次开发和商用，但仍要保留许可证、版权和变更声明等法定义务。
- 仓库确实包含 [管理端和 UniApp 前端源码](https://github.com/crmeb/CRMEB/tree/master/template)，并非只有后端。
- [CRMEB 的 Composer 配置](https://github.com/crmeb/CRMEB/blob/master/crmeb/composer.json) 从 PHP 7.1 起步，README 列出的运行环境为 PHP 7.1–7.4；同时使用 Vue 2、Element UI 以及一批较旧的固定依赖。
- 项目在 2026 年仍有 [代码提交](https://github.com/crmeb/CRMEB/commits/master/)，所以问题不是“无人维护”，而是公开版本的技术基线较旧。
- PHP 官方当前支持分支见 [Supported Versions](https://www.php.net/supported-versions.php)。PHP 7.x 已不在支持列表，因此 CRMEB 不能原样部署后直接视为生产安全。

### 为什么 ShopXO 更适合第一版

- [ShopXO 仓库](https://github.com/gongfuxiang/shopxo)采用 MIT 许可证，并明确支持微信小程序等多端。
- [Composer 配置](https://github.com/gongfuxiang/shopxo/blob/master/composer.json)要求 PHP ≥8.0；正式部署仍应选 PHP 官方当前受支持的小版本。
- [ShopXO UniApp](https://github.com/gongfuxiang/shopxo-uniapp)是独立完整前端源码，便于重做成参考图中的横向游戏栏、左侧分类和右侧套餐列表。
- 它仍是普通商城，不自带真正的选手派单平台。推荐它的前提是第一版由后台人工派单。

## 四、建议的第一版范围

### 顾客端

- 微信登录；
- 六个游戏分类；
- 服务分类与套餐列表；
- 套餐详情和动态下单参数；
- 微信支付；
- 我的订单与服务进度；
- 退款/售后申请；
- 微信原生客服入口；
- 用户协议、隐私政策和服务规则。

### 管理后台

- 游戏、服务分类、套餐和价格管理；
- 订单查询、人工派单、状态更新；
- 支付通知、退款和对账记录；
- 顾客和服务人员基础档案；
- 售后与争议记录；
- 操作日志、角色权限、数据备份。

### 第一版暂不做

- 选手自主注册和资质审核；
- 抢单大厅、自动匹配和复杂排班；
- 顾客与选手的自建即时聊天；
- 平台抽佣、自动分账和提现；
- 多商户入驻；
- 优惠券、分销、直播等与核心闭环无关的商城功能。

这个范围仍能呈现与参考图相近的顾客体验，但能显著降低开发、审核、财务和风控复杂度。

## 五、微信能力的正确接入方式

### 登录

小程序调用 `wx.login` 获取一次性 `code`，由服务端换取用户标识并建立自身登录态。AppSecret、会话密钥和支付私钥不得放在小程序前端。官方入口：[小程序登录](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/login.html)。

### 客服

第一版优先使用小程序 `button` 的 `open-type="contact"`，直接进入微信客服会话；无需自建消息系统。官方组件文档：[button](https://developers.weixin.qq.com/miniprogram/dev/component/button.html)。

### 微信支付

基本流程应为：

1. 服务端创建平台订单并锁定应付金额；
2. 服务端调用微信支付 APIv3 预下单；
3. 小程序使用服务端返回参数调用 `wx.requestPayment`；
4. 服务端验证并解密支付通知，幂等更新订单；
5. 支持主动查单、关单、退款和每日对账。

微信支付官方 SDK 明确提供自动签名、验签、回调处理和解密能力，并要求商户号、商户 API 证书/私钥及 APIv3 密钥。参见 [微信支付 APIv3 Java SDK](https://github.com/wechatpay-apiv3/wechatpay-java) 与 [APIv3 接口规则](https://pay.weixin.qq.com/docs/merchant/development/interface-rules/introduction.html)。无论最终使用 Java 还是 PHP，都应遵守相同的服务端安全边界。

仅收到前端“支付成功”不能作为订单已付款依据，必须以经过验签的服务端通知或主动查单结果为准。

## 六、上线前必须先过的风险门槛

1. **经营模式**：先确定是平台自营服务，还是允许第三方选手入驻并抽佣。后者可能涉及电子商务平台经营者义务、结算、税务以及增值电信业务许可判断，应按主体和实际模式咨询专业机构。
2. **主体和支付**：需要可用的小程序主体、与业务匹配的服务类目，以及能为该业务开通的微信支付商户能力；不要先开发完再发现类目或支付无法通过。
3. **游戏规则**：逐款核对发行商用户协议。代练、代打、账号共享、账号/道具交易和外挂相关服务的风险不同，不能统称为普通“游戏服务”。
4. **商标和素材**：开源代码许可证不授予英雄联盟、永劫无间、王者荣耀等游戏名称、Logo、角色图和宣传图的商业使用权。参考图里的品牌图标与商品图不能直接复制上线。
5. **隐私与账号安全**：只收集完成服务所必需的数据，明确用途、保存期限和删除机制；避免收集账号密码、身份证照片和无关聊天内容。
6. **售后规则**：服务开始前后分别如何退款、未按时接单如何处理、如何举证和申诉，必须在支付前向顾客明确展示。
7. **高价与“保底”表达**：参考图中数千元服务及“必出、保底”描述容易引发投诉和支付风控，需要真实可交付、清晰限制条件和完整履约证据。

## 七、粗略工期判断

以下仅为范围判断，不包含主体注册、备案和微信审核等待时间：

- 单商户、人工派单 MVP：2 名熟悉现有底座的开发人员约 4–7 周；
- 增加独立选手端、抢单、聊天、评价：再增加约 5–8 周；
- 增加自动分账、提现、复杂风控和成熟争议处理：通常应按 3–6 个月的正式平台项目评估。

决定工期的不是六个游戏分类，而是是否存在选手侧、账号交接、实时消息、资金结算和售后争议。

## 八、待审核的推荐方案

### 推荐方案 A：先做可上线的单商户版本

- 底座：ShopXO + ShopXO UniApp；
- 业务：服务商品、服务订单、后台人工派单；
- 客服：微信原生客服；
- 支付：微信支付 APIv3；
- 底部导航：首页、分类、订单、客服、我的；
- 后续确认商业可行后再扩展选手端。

这是成本、速度和风险最平衡的方案。

### 备选方案 B：直接做双边派单平台

- 小程序：顾客与选手两个角色或两套端；
- 后台底座：RuoYi-Vue-Plus 等 MIT 脚手架；
- 自建：服务目录、报价、派单、接单、履约、评价、争议和结算模块；
- 商城项目只作业务参考，不作为核心领域模型。

只有在选手自主接单和平台抽佣是第一天就必须存在的商业闭环时，才应选择方案 B。

## 九、下一步需要确认的三个问题

1. 第一版是后台人工安排自己的服务人员，还是允许外部选手注册并自主接单？
2. 实际售卖的是陪玩、护航/代打、段位代练、指定任务，还是游戏道具/账号？服务人员是否需要登录顾客账号？
3. 是否已经有公司/个体工商户、小程序账号和微信支付商户号？

确认这三项后，再进入“任务拆分和开发计划”，此时才能准确决定采用 ShopXO、CRMEB，还是自建双边平台。
